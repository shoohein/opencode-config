# ADR 004: レビュアーおよびプランエージェントを自問形式で設計する

## コンテキスト

レビュアーエージェントおよびプランエージェントは、「何が問題か」「どの設計を採るか」といった判断を行う。判断の質はプロジェクトの品質に直結する。

LLM は以下の構造的制約を持つ:

- セッション間で学習しない。過去の失敗は次のセッションに反映されない。
- 訓練スナップショットで固定された「価値観の模倣」しか行えない。
- 個体としての意思決定プロセスを内部に持たない。

この制約下で判断品質を担保する方法として、以下の 3 つの素朴なアプローチにはそれぞれ致命的欠点がある:

- **ルール列挙型**: プロンプトに criteria を積み上げる。失敗のたびに追記され、情報エントロピーが増大し、重要な指示が埋没する。
- **人間介在型**: 判断を全て人間に戻す。スケールしない。
- **模倣許容型**: LLM に「それらしく」判断させ人間が最終検証する。模倣の正誤を検知する仕組みがなく、人間の負荷が減らない。

いずれも「LLM の出力に判断プロセスが内部化されていない」という根本問題に対処していない。

## 判断

### 1. レビュアー・プランエージェントに自問形式を採用する

- **決定:** 対象エージェントの Criteria セクションを「問い（question）」の集合として設計する。エージェントは判断を下す前に、該当する問いを自己に投げ、回答し、その Q&A チェーンとともに finding を出力する。回答が「問題なし」を示す場合、finding は生成されない。証拠不十分で回答不能な場合も finding は生成せず、捕捉問い（原則 5）で「判断に必要な情報が不足していた」と報告してもよい。
- **理由:** 問いは「価値観そのもの」を外部化する。LLM 内部に価値観がなくても、問いに答えるプロセスを通じて意思決定プロセスを模倣させることができる。問いは criteria リストと異なり、失敗のたびに肥大化しない。失敗が観測されたときは「問いの質」が原因であり、問いを修正することで根本対処ができる。

### 2. 問いの設計原則を明文化する

- **決定:** 問いは以下の 5 原則に従う:

  **1. 「なぜ」に還元可能である:** 問いは表明ではなく説明を強制する。✓ "Does this length obscure the reader's understanding of the algorithm?" ✗ "Is this function too long?"

  **2. 反例を許容する:** 問いは「問題なし」を正当な回答として認める。✓ "Would splitting this function fragment a coherent unit of knowledge?" ✗ "Split this function if it exceeds 30 lines."

  - **opposing pair（対立構造）の適用:** 可能な場合、問いは不足と過剰の両方向から概念を捉える 2 項対立の形式で記述する。一方の問いは「不足（足りない）」を検出し、他方は「過剰（多すぎる）」を検出する。これにより問いは自動的に「問題なし」も正当な回答として認める構造を持つ。文法チェックや一方向の誤り検出（綴りミス等）など、機械的判定に近い概念では対立を無理に作らず単一方向の問いで留める。

  **3. 成果物に自己参照する:** 問いは一般原則の適用ではなく、目の前の成果物への直接的な観察を要求する。✓ "Does this name mislead about what the function actually does here?" ✗ "Are names in this codebase clear?"

  **4. 連鎖可能である:** 一つの問いが次の問いを引き出す。段階的に本質へ降りていく。例: "Can I describe this function in one sentence?" → when "and" appears → "Do the parts share state or reason for change?" → when the answer is no → "If split, would each part be independently understandable?"

  **5. 捕捉問いを含む:** 定義された問いは有限であり、事前定義されたどの問いにも該当しない問題は必ず発生する。捕捉問いは「定義外の問題」を掬う安全網として機能する。例: "Is there something about this code that makes me uncomfortable, that none of the above questions have addressed? If so, describe the discomfort and how to investigate."

- **理由:** 原則がないと、問いが表面的な yes/no チェックに退化する。原則は問いのメンテナンス基準としても機能し、問いを追加・修正する際の判断根拠を提供する。

### 3. 適用範囲をレビュアーおよびプランエージェントに限定する

- **決定:** 本パターンは判断を行うエージェント（レビュアー、プランナー）に適用する。メタスキル（create-\*）とタスクスキル（git-commit, doc-review-cycle）は対象外とする。
- **理由:** メタスキルの判断は対話的でありユーザー確認が入るため、自問形式の必要性が低い。タスクスキルは決定論的手順の実行であり判断を含まない。スコープを絞ることで、パターンの検証と定着を優先する。将来、メタスキルへの拡張は成功実績を踏まえて検討する。

### 4. Q&A チェーンを出力に含め反証審査の対象とする

- **決定:** 対象エージェントは finding ごとに「その finding を導いた問いと回答」を必須項目として出力する。出力フォーマット（既存の doc-reviewer YAML 互換）:

  ```yaml
  findings:
    - location: string
      question: string # この finding を導いた問い
      answer: string # 文書/コードの証拠に基づく回答
      severity: critical | major | minor
      suggestion: string
  ```

  問いチェーンが「finding 不発生」または「回答不能」（判断 1 参照）で終了した場合、出力は生成されない。「問題なし」の声明は出さない。

  この Q&A チェーンは superagent（doc-review-cycle スキル）による反証審査の対象となる。superagent は各 finding の Q&A を読み、証拠の十分性・推論の妥当性・反証可能性を評価する。推論に飛躍がある finding、文書の具体的記述に基づかない finding は、レビュアーの severity に関わらず却下される。これは LLM が出力した判断を LLM が再検証する二段構えの品質ゲートであり、自問形式の完成に不可欠な構成要素である。

- **理由:** 判断プロセスの可視化が本アーキテクチャの核心。プロセスが不可視な finding は、従来型 criteria レビュアーと区別がつかず、失敗の原因追跡ができない。

### 5. Criteria セクションの記載形式を統一する

- **決定:** 対象エージェントの Criteria セクションは「概念キーワード + 具体的な問い」の形式で記述する。

  対立構造を持つ概念（opposing pair）:

  ```
  - **{Concept}**:
    - {不足側の問い}
    - {過剰側の問い}
  ```

  対立構造を持たない概念:

  ```
  - **{Concept}**: {単一の問い}
  ```

  例: `- **Depth**: Does the question require reasoning beyond a surface check?`

  概念が多い場合、`###` 見出しで評価軸をグループ化してもよい。見出しは概念キーワードを兼ね、bullet には質問のみを書く:

  ```
  ### Scannability

  - Can I understand what this document covers by reading only the headings?
  ```

  捕捉問い（原則 5）は評価軸リストの末尾に配置し、空行や見出しで視覚的に分離する。これは「評価軸の 1 つ」ではなく「定義された問いでは拾えなかったものを拾う」役割を構造で示すためである。

- **理由:** 概念キーワードだけでは LLM は行動指針を構成できない。問いだけでは何を評価しているかが不明瞭になる。両者を並置することで抽象概念と具体的行動が結合する。また、キーワード単位でのエージェント間比較・整理が容易になる。

## 検討した代替案

<!-- optional: 判断に含まれない全体的な代替案があれば記載 -->

- **代替案:**
  - ルール列挙型 criteria の継続: 現状の doc-reviewer, code-reviewer のように criteria をルールリストで持つ
    - **不採用理由:** 失敗時の原因分析が困難で、プロンプトが肥大化し情報エントロピー増大により重要な指示が埋没するため
  - 人間による全レビュー: 判断を LLM から人間に戻す
    - **不採用理由:** 単一プロジェクトの規模でも維持不能であり、プログラマの「怠惰」の美徳に反するため
  - 模倣型 + 人間検証: LLM に判断させ人間が結果を検証する
    - **不採用理由:** 人間の検証負荷が減らず、模倣の限界（見た目のパターンマッチ）を突破できないため
  - 外部ルールベース評価器（例: Cursor rules, .cursorrules）
    - **不採用理由:** ルールをコード外に置くが、本質はルール列挙型と同じであり、同様の欠点があるため

## 結果

### ポジティブ

- **失敗原因の追跡可能性**: 誤った finding が出た場合、Q&A チェーンを見ることで「問いが悪い」「回答が浅い」「そもそも問いが無かった」のいずれかを特定できる。
- **問いの再利用性**: よく設計された問いは複数のレビュアー間で共有可能。ドキュメントとコードの両方で「命名は意図を表しているか」は問える。
- **メンテナンスコストの上限**: 問いは価値観のカテゴリに縛られ、失敗事例のたびに増えない構造を持つ。
- **教育モデルの反映**: 「答えではなく道を示す」という大学院生教育のモデルを実装に落とし込める。

### ネガティブ

- **問いの品質が人間依存**: 問いの初期設計と改善は人間の判断に依存し、自動化できない。悪い問いは悪い finding を生むため、問いの設計者（プロジェクト参加者）が問いの品質に対して責任を持つ。
- **問い漏れは検出不可**: 未知の評価観点に対しては、対応する問いが無い限り検出できない。捕捉問いで軽減するが完全ではない。
- **Q&A チェーンの検証コスト**: 人間の検証負荷はゼロにならない。ただし「finding の正誤判定」から「Q&A チェーンの論理性検証」に変わり、後者は前者より速い。
- **問いの粒度設計の困難さ**: 抽象的すぎる問いは表面的な回答を許し、具体的すぎる問いはルール列挙に退化する。適切な粒度の見極めが必要。
- **既存エージェントの書き換え作業**: doc-\*, code-\* 各エージェントの Criteria セクションを問い形式に再設計する必要がある。

# ADR 001: スキル設計原則

## コンテキスト

OpenCode のスキルシステムにおけるスキル間の依存関係、メタスキルの責務、入出力設計の基本方針を確立する。これらの原則は `create-skill` をはじめとするスキル作成スキル群の実装基盤となる。

## 判断

### 1. 基本理念：エージェントはシェル、スキルはコマンド

- **決定:** スキルは他のスキルやコマンド、エージェントといった外部ファイルに静的な依存関係を持たない。一つのことに集中し独立して完結する（Do one thing well）。スキルのオーケストレーションはすべてエージェントが動的に行う。
- **理由:** コンパイラによる静的チェックが存在しないため、依存関係を許容すると変更時の影響範囲が追跡不能になり、システム全体のエントロピーが増大する。共通処理も独立したフィルタとして切り出し、エージェントの推論でパイプラインとして繋ぐことで、KISS 原則と高いコンポーザビリティを両立する。

### 2. メタスキルの最重要責務：インターフェースのコンパイラ

- **決定:** メタスキル（スキルを作成するスキル）の最も重要な役割は、エージェントが迷わずにツールを呼び出せるよう、宣言的かつ一意なメタデータ（`description`）を生成することとする。
- **理由:** OpenCode のスキルは遅延読み込みされる。エージェントはタスク実行時にインデックス化された `description` だけを頼りに必要なスキルを探索する。静的依存関係を排除した結果、LLM の推論が唯一の結合点となるため、名前空間の衝突を防ぎ、各スキルの役割を完全に直交させるための厳格なインターフェース定義をメタスキルに強制する必要がある。

### 3. 既存スキルのインデックス調査（作成前プロセス）

- **決定:** 新しいスキルを作成する前に、既存スキルの名前と説明文のリストのみを読み込み、重複や直交性を確認する。`SKILL.md` の本文（実装）までは読み込まない。
- **理由:** 全文読み込みはスキル数増加に伴いコンテキストウィンドウを圧迫し、レイテンシ増大とトークンコストを招く。一方、調査省略は意味論的な重複を生み、実行時のエージェント推論が破綻する。事前の軽量調査により、実行時の甚大な失敗リスクを防ぐ。

### 4. スキルの標準入出力：構文から意味へ

- **決定:** スキル内で JSON スキーマのような厳密なデータフォーマットを指定しない。代わりにどの情報を入力とし、どの情報を出力するかのみを定義する。構造化データへの変換が必要な場合は、独立した別スキルとして作成する。
- **理由:** LLM 最大の強みである自然言語による曖昧さの吸収と、プレーンテキストストリームの普遍性を活かすため。外部 API の仕様変更等でデータフォーマットが変わっても、情報の意味が変わらなければスキルの修正が発生しない堅牢な設計を実現するため。

### 5. HITL とフォールバックの許容

- **決定:** スキルには、入力情報に不足がある場合や推論に迷った際に、ユーザーに質問するフォールバック行動を明記する。ただし、文脈からの自明な推論は勝手に進めるよう制約を設ける。
- **理由:** 例外処理やエッジケースの条件分岐をプロンプト内にすべて網羅する労力を捨てるため。LLM がハルシネーションを起こして嘘の情報で後続パイプラインを汚染するのを防ぐため。クリティカルな分岐でのみブロックして質問するバランスを取る。

### 6. テスト戦略とフェイルセーフ（実用主義）

- **決定:** スキルに対する厳密な単体テストフレームワークは構築しない。ただし、ファイルの削除や DB の更新などの破壊的変更を伴うスキルにのみ、実行前の dry-run とユーザー承認を強制する。
- **理由:** LLM の非決定的な出力に対する脆いテストを保守し続けることは将来の負債となる。エラーが生じた場合は、その場で `SKILL.md` の自然言語を数行修正する最速のフィードバックループを回す方が、個人の生産性向上において理にかなっている。

## 結果

### ポジティブ

- スキル間の依存関係がゼロになり、各スキルの保守・修正が他のスキルに波及しない
- `name` + `description` による軽量インデックスで、スキル数増加時の探索コストが線形に留まる
- 意味ベースの入出力設計により、外部仕様変更に対する耐性が高い
- HITL フォールバックと dry-run の組み合わせで、破壊的操作のリスクを最小化しつつ非破壊的操作の速度を維持

### ネガティブ

- エージェントの推論品質に依存するため、誤ったスキル選択やオーケストレーションの失敗があり得る
- 自然言語ベースのインターフェースは実行時まで型安全性を提供しない
- メタデータのみの重複検出では、深い意味的重複を見逃す可能性がある

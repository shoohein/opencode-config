# ADR 002: エージェント設計

## コンテキスト

OpenCode ではエージェントに指示を与える手段として、グローバルな `instructions`（全セッションで常時読み込まれる、`opencode.jsonc`）とエージェント固有の定義ファイル（`agents/<name>.md`）の 2 つが組み込みで提供されている。

本リポジトリは `~/.config/opencode` に配置する設定リポジトリであり、`agents/` が正規のエージェント定義パスである。OpenCode は `.opencode/agents/` も探索するが、当プロジェクトでは `agents/` → `.opencode/agents/` のシンボリックリンクで対応する。

問題点：

- グローバルな指示はすべてのセッションで読み込まれるため、タスクに関係のない内容（例：バグ調査中にレビュー基準が読み込まれる）までコンテキストを圧迫する。
- エージェント定義ファイルは単一ファイルであり、ネイティブな合成機構を持たない（`agent.<name>.prompt`（OpenCode 設定でエージェントプロンプトを上書きする機構）は上書きでありマージではない）。
- 実装者とレビュー担当者が同じコーディング価値観（KISS, YAGNI, DRY（Don't Repeat Yourself）等）を共有しないと、レビュー担当者が実装者の想定外の指摘をする摩擦ループが発生する。

## 判断

### 1. アーキテクチャ

- **決定:** エージェントへの指示を 3 層に分離する。各層は異なるタイミングで読み込まれる：

  ```
  Global instructions (opencode.jsonc)
    └─ 運用メタデータのみ（タスク管理、ドキュメントポリシー等）
    └─ コーディング価値観や評価基準はグローバル指示には含めない

  Skills（skill() ツールでオンデマンド読み込み）
    └─ coding-principles ← KISS, YAGNI, DRY 等

  Agents（agents/<name>.md）
    └─ Role / Input / Output（常時必須）
    └─ Criteria（レビュー担当エージェントのみ — 評価次元）
  ```

- **理由:** 各層は読み込み特性が異なる — グローバル指示は常時、スキルは遅延読み込み、エージェントは起動時のみ。コンテンツを適切な層に割り当てることで、各セッションのコンテキストを必要な情報だけで構成し、他タスクの圧迫を防ぐ。また ADR 001 の静的依存禁止（判断 1）と遅延読み込みの原則に従い、スキルはエージェントが実行時に動的に選択する。

### 2. ルール

#### 2.1 単一ファイルエージェント

- **決定:** 各エージェントは `agents/<name>.md` の単一ファイルで定義する。`{file:}`（OpenCode のファイル参照構文）による外部ファイル合成も、`agent.<name>.prompt` による上書きも使用しない。
- **理由:** 単一ファイルは管理が単純であり、合成機構がない以上、1 ファイルに閉じる以外に一貫性を保つ手段がない。`{file:}` 構文は URL からの読み込みに対応していないため、リポジトリ間の命令共有に使用できない。

#### 2.2 最小セクションと拡張

- **決定:** すべてのエージェントファイルは最低限 Role（役割）、Input（入力）、Output（出力）の 3 セクションを持つ。エージェントが起動時に常に読み込むべきドメイン固有の指示がある場合は追加セクションを許可する。例：レビュー担当エージェントは `# Criteria` セクションを追加する。
- **理由:** Role / Input / Output はエージェントの責務範囲とインターフェースを定義する最小構成である。追加セクションは特定のエージェントタイプに閉じた情報を置く場所として、ファイル肥大化を避けつつ拡張性を確保する。

#### 2.3 共有コーディング原則のスキル分離

- **決定:** コーディング原則（KISS, YAGNI, DRY 等）は `coding-principles` スキルに集約し、個々のエージェントファイルには埋め込まない。実装者とレビュー担当者の両方がこのスキルを読み込むことで価値観を共有する。
- **注記:** `coding-principles` は標準スキルフォーマット（What I do / When to use me / Scope / Workflow）のうち Workflow セクションを持たない特殊形式を取る。原則の参照のみを目的とし、ツール呼び出しを伴わない。
- **理由:** 複数のエージェントに同一の原則を重複記述すると更新時の不整合リスクが生じる。スキルとして分離することで単一の更新元を保ち、遅延読み込みにより必要な時だけ読み込まれる。また ADR 001 の静的依存禁止に従い、エージェントはスキルに静的に依存せず、実行時に動的に選択する。

#### 2.4 グローバル指示の範囲制限

- **決定:** グローバル指示（`opencode.jsonc` の `instructions` 配列）には、プロジェクト全体の運用メタデータ（タスク管理、セッション状態、ドキュメントポリシー、クリティカルシンキングガイドライン）のみを含める。コーディング価値観やレビュー基準は含めない。
- **理由:** グローバル指示は全セッションで読み込まれるため、タスクに関係のない内容が常にコンテキストを消費することを防ぐ。メタデータだけを常駐させることで各セッションのコンテキスト効率を最大化する。

#### 2.5 レビュー基準のエージェント埋め込み

- **決定:** レビュー担当エージェントの評価基準は、グローバル指示ではなく各エージェントファイルの `# Criteria` セクションに記述する。
- **理由:** レビュー基準は特定のレビューセッションでのみ必要であり、全セッションで読み込む根拠がない。レビュー担当エージェントの起動時にのみロードすることで他タスクのコンテキストを汚染しない。

#### 2.6 Scope セクションの条件付き導入

- **決定:** エージェントの責務境界が単一の場合は Role 文で表現し、`# Scope` セクションを設けない。境界が 2 点以上（in/out + 他 reviewer への委譲先 等）で Role にマージすると 3 文を超える場合は `# Scope` セクションを追加する。
- **理由:** 構造化の恩恵（スキャン性、拡張性）は境界が複雑な場合にのみ顕在化する。単純な境界を Scope セクションに分離すると情報の重複とセクション増加による認知負荷増大が上回る。

### 3. メカニズム

- **決定:** スキルの遅延読み込みは OpenCode ネイティブの `skill()` ツールに依拠する。`<available_skills>`（システムプロンプトに含まれるスキル一覧）に name + description が常時表示され、エージェントが必要と判断した時点で `SKILL.md` 全文が注入される。
- **理由:** `skill()` ツールは OpenCode の組み込み機能であり、追加のプラグインや設定を必要としない。OpenCode の権限設定により、サブエージェントも共有スキルを読み込める。

## 検討した代替案

- **`{file:}` によるファイル合成:** URL から読み込めないため、リポジトリ間での命令共有に使用不可。没。
- **全指示のグローバル配置:** タスクに関係のない内容（レビュー基準やコーディング原則）がすべてのセッションで読み込まれ、コンテキストを圧迫する。没。
- **プラグインベースの動的注入:** OpenCode プラグインはシステムプロンプト合成のためのフックを公開していない。没。
- **`agent.<name>.prompt` によるインライン上書き:** エージェントファイルの内容を合成・拡張するのではなく置換するため、ファイルベースの管理と競合する。没。

## 結果

### ポジティブ

- タスクに関係のない指示がコンテキストを消費しない（バグ調査時にレビュー基準が読み込まれない）
- 実装者とレビュー担当者が同一の `coding-principles` スキルを共有し、レビューの摩擦が減少する
- エージェントは単一ファイルで完結し、管理が単純
- `{file:}` に依存しない設計 — OpenCode の組み込み機構のみで動作する

### ネガティブ

- エージェントがスキルの説明文だけを頼りに `coding-principles` をロードするか判断するため、description の品質に依存する
- すべてのスキルの name + description が常にシステムプロンプトに含まれる

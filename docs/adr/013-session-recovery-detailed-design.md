# ADR 013: セッション回収機構の詳細設計

## コンテキスト

ADR 009 はセッション回収アーキテクチャの基本方針（別プロセス spawn、サイレント完結、ADR 抽出）を定めたが、以下の項目を詳細設計に先送りした：

- トリガー方式（cron / systemd timer / OpenCode 起動時フック / ハイブリッド）
- 回収処理のリソース分離と回収用モデル
- 回収実行中にユーザーが同一プロジェクトで新セッションを開始した場合の競合

本 ADR はこれらの先送り項目を含む、回収機構全般の詳細設計判断を記録する。

## 関連 ADR

- **ADR 009:** セッション回収アーキテクチャ — 本 ADR の上位決定。spawn 方式、サイレント完結、ADR 抽出の基本方針
- **ADR 007:** セッションライフサイクル — Stateless Session Operation、SSoT（Single Source of Truth）は現状

## 判断

### 1. トリガー方式

- **決定:** プラグインの `session.created` イベントフックを用い、ユーザーセッション起動時に 1 回だけ放置セッションのスイープを実行する。cron や systemd timer は使用しない。
- **理由:** 本システムが動作する Debian コンテナには cron / systemd が不在であり、外部スケジューラに依存しない方式が最もポータブルである。ユーザーが作業を再開したタイミングで回収が走る自然な流れでもあり、UX 目標（ユーザーが回収を意識しない）に合致する。
- **代替案:**
  - `chat.message` フックによる毎メッセージ発火
    - **不採用理由:** 回収セッション自身も `chat.message` を発火するため暴発リスクがある。軽量タスクでも全セッション走査が発生し、無駄な API 呼び出しが蓄積する。
  - cron / systemd timer
    - **不採用理由:** コンテナに不在であり、導入にマシン依存のセットアップが必要なため。
- **トレードオフ:** ユーザーが OpenCode を起動しない限り回収は走らない。ただし放置セッションは元々 3 時間以上放置されているため、起動遅延は誤差範囲である。

### 2. 回収スコープ

- **決定:** 1 回の回収セッションにつき、1 つの放置セッションのみを回収する。複数の放置セッションがある場合は、`time.updated` が最も古い 1 件を対象とし、残りは次回以降のユーザーセッションで順次処理する。
- **理由:** 1:1 モデルは失敗境界が明確で、部分失敗時に「どのセッションの回収に失敗したか」が特定しやすい。複数放置は次回セッションで自然にシリアライズされるため、全件一括処理の複雑さ（ループ中断、部分失敗の回復）に見合う UX 差がない。
- **代替案:**
  - 全件一括回収
    - **不採用理由:** 1 件失敗時の後続処理判断が複雑であり、LLM 消費も集中する。典型的な放置数は 1 件であり、複数放置が発生しても次回セッションで逐次解消されるため、一括処理の価値が低い。
- **トレードオフ:** バックログ解消に複数セッションを要するが、ユーザーは回収を意識しないため体験上の差はない。

### 3. 放置セッションの検出

- **決定:** OpenCode の `client.session.list()` と `client.session.status()` から取得した情報を SSoT（Single Source of Truth、ADR 007 §2）とし、以下の条件で放置セッションを判定する。`time.updated` はユーザー意図の中断ではなく、OpenCode セッション更新時刻に基づく操作的近似である。
  1. タイトルが `【完了】`、`【中断】`、`【回収】` のいずれかの接頭辞で始まる → スキップ
  2. `time.created` が導入 epoch 以前 → スキップ（導入前セッション）
  3. `SessionStatus` が `busy` または `retry` → スキップ（稼働中）
  4. `now - time.updated > 3h` → 回収対象
  5. 上記を満たすセッションが複数ある場合、`time.updated` が最古の 1 件を選択
- **理由:** 外部状態ファイルや二重管理を避け、OpenCode 自身が持つデータを SSoT として活用する。接頭辞によるスキップは、処理済みセッションの再回収を防ぐ安全装置として機能する。`retry` 状態をスキップするのは、API の到達不能・クレジット不足等の異常時には回収セッションも同様に API を利用できず、回収が不可能なためである。3 時間という閾値は、人間の集中力による 1 タスクの区切りを基準とした（運用で調整可能）。
- **代替案:**
  - 外部 Manifest ファイルに放置時刻を記録
    - **不採用理由:** OpenCode 本体との二重管理リスク（ADR 007 §2）。
- **トレードオフ:** `time.updated` はタイトル更新や内部処理でも変動しうるため、「ユーザー作業が中断された」ことの保証にはならない。これは操作的近似として受容する。

### 4. 導入前セッションの除外

- **決定:** `.opencode/.recovery-epoch` ファイルに初回起動時の現在時刻をエポック ms で記録し、`time.created` が epoch 以前のセッションは回収対象外とする。epoch ファイルにはコメント行 `# do not delete` を付与する。
- **理由:** セッション管理システム導入以前のセッションは手動で ADR 抽出等が行われている可能性があり、再回収による重複処理を防ぐ必要がある。epoch ファイルが削除されても、`【完了】`/`【中断】` 接頭辞が付与された既回収セッションは保護されるため、安全側に倒れる。
- **代替案:**
  - 基準セッション方式（接頭辞 `【基準】` を持つセッションを epoch 代わりに使う）
    - **不採用理由:** インフラ情報（導入時刻）をセッションタイトルに入れるのは責務違反である。タイトル変更で後方互換性が損なわれる脆弱性もある。
- **トレードオフ:** ファイルシステムに依存する（マシンローカル）。削除されると導入前未処理セッションが再回収対象になる可能性がある。

### 5. 競合制御

- **決定:** `.opencode/.recovery.lock` ファイルで回収セッションの排他制御を行う。形式は `{"recovery_session_id": "...", "started_at": <epoch_ms>, "ttl_ms": 600000}`。回収チェック時に lock が存在する場合：
  - 対象セッションの `SessionStatus` が `busy` または `retry` → TTL に関係なくスキップ（稼働中として信頼）
  - `SessionStatus` が `idle` または 404 → `now - started_at > ttl_ms` なら stale とみなし上書き再 spawn
  - `now - started_at <= ttl_ms` → 正常完了直後とみなしスキップ
- **理由:** `busy` 信頼により、長時間実行中の回収セッションを TTL 超過で誤って上書きする無限ループを防止する。TTL は `idle` なのに lock ファイルだけが残った異常ケースのゴミ掃除として機能する。
- **代替案:**
  - TTL 超過時に `busy` も上書き
    - **不採用理由:** 本質的に処理時間が長い回収が TTL 超過を繰り返すと、一生上書きを重ねる無限ループに陥る。
- **トレードオフ:** TTL（10 分）は回収セッションの想定最大実行時間に依存する。運用で調整が必要になる可能性がある。

### 6. 回収セッションの自己終端

- **決定:** 回収セッションは正常終了時に自身のタイトルを `【完了】` に更新する。クラッシュした場合は接頭辞なしで放置されるが、3 時間後にメタ回収の対象となる（このチェーンは ADR 009 の意図に沿う）。
- **理由:** 回収セッションも通常セッションと同じく Stateless Session Operation の対象であり、処理済みを示す表示機構が必要。自己終端により、回収セッションが放置された場合の無限回収ループを防止する。
- **トレードオフ:** 回収セッションのクラッシュ時はメタ回収が必要になるが、これは設計上の想定内である。

### 7. 回収セッションの視認性

- **決定:** 回収セッションは spawn 時にタイトルに `【回収】` 接頭辞を付与する。OpenCode がタイトルを自動更新する可能性があるため、`session.updated` イベントで接頭辞の再適用を行う。
- **理由:** セッション一覧でユーザーが開始したセッションとシステムが自動起動したセッションを人間が判別できるようにする。
- **トレードオフ:** OpenCode のタイトル自動更新が現行バージョン（v1.17.9）で実際に発生するかは未検証。発生しない場合は再適用フックは不要（実装時に検証する）。

### 8. WIP コミットの扱い

- **決定:** 回収セッションでは WIP コミットを作成しない。未コミット変更はユーザーの次回セッションで `git status` により発見される。WIP コミットは正常終了（`session-close` スキル）時のみ作成する。
- **理由:** 回収セッションの WIP コミットは、ユーザーが編集中のワーキングツリーと競合するリスクがある。未コミット変更の保護は正常終了時の責務とし、回収は情報整理（要約・タスク更新・ADR 抽出・接頭辞付与）に徹する。
- **代替案:**
  - 回収時にも WIP コミットを作成する
    - **不採用理由:** ユーザーが同一プロジェクトで並行して編集を開始した場合、回収セッションが背後で `git add -A && commit` を実行する競合が発生する。ADR 009 が先送りした「同一プロジェクトでの競合」の詳細設計として、作成しない判断が最も安全である。
- **トレードオフ:** 放置セッションの未コミット変更がコミットされずに残る。ただし変更は失われず、ユーザーが次回セッションで認識できる。

## 結果

### ポジティブ

- 回収機構の実装に必要な全判断が確定し、実装の指針が明確になった
- 外部スケジューラに依存しないポータブルな設計
- `busy` 信頼 + TTL により、クラッシュ時の自動回復と無限ループ防止を両立
- 導入前セッションの重複処理リスクを epoch ファイルで防御
- 回収時 WIP コミット競合を原理的に排除

### ネガティブ

- `time.updated` は「放置」の保証ではなく操作的近似である（基本設計書に明記済み）
- 回収がユーザーセッション起動に依存するため、長期不在時は放置セッションが蓄積する
- TTL の妥当性は運用による調整が必要

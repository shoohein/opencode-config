# ADR 001: タスク管理システムのアーキテクチャ判断

## ステータス

Accepted (2026-07-04)

## コンテキスト

OpenCode エージェント上で動作するタスク管理システムを設計するにあたり、以下の4つのアーキテクチャ上の意思決定が発生した。いずれもシステム全体の設計思想を決定づける判断であり、後続の実装判断（ADR 002）の前提となる。なお、Next Action/Worklog 分離や Unix 哲学の採用理由など、本 ADR で直接判断を記録していない設計意図は基本設計書の Rationale（§5）に詳述する。

## 判断一覧

### 1. 状態管理方式 — ディレクトリ配置を Single Source of Truth とする

- **決定:** タスクの「状態」は所属ディレクトリのパス（`pending/` / `in_progress/` / `done/` / `canceled/`）を唯一の真実の源泉とする。YAML Front Matter に `status` フィールドを持たせない。
- **代替案:** メタデータ内に `status: in_progress` を保持し、ディレクトリ配置と二重管理する。
- **却下理由:** ディレクトリとメタデータの二重管理は DRY 原則に反する。必ず「ディレクトリは done/ なのに status は in_progress のまま」という不整合が発生する。Unix におけるファイル移動（`mv`）はアトミックな操作であり、状態遷移の信頼性を OS カーネルレベルで保証できる。
- **トレードオフ:**
  - 人間の誤操作（誤った `mv` やファイル名の手動変更）により状態が破損するリスクがある。ただし、このシステムでは全ての状態変更をエージェントが仲介するため、人間が直接ファイル操作を行うシナリオは稀。
  - ディレクトリ名の変更（例: `in_progress` → `wip`）が発生した場合、全タスクのパス解決に影響する。命名の安定性が前提となる。

### 2. ID 採番ロジック — 動的走査（毎回最大値 +1）

- **決定:** タスク作成時に `tasks/` 配下（`archive/` 含む全ディレクトリ）の `.md` ファイルを走査し、ファイル名の3桁連番の最大値を抽出して +1 した値を新 ID とする。
- **代替案:** `.next_id` や `status.md` などのインデックスファイルを作成し、そこで ID を中央管理する。
- **却下理由:** インデックスファイルの更新漏れや、エージェントと人間の同時操作による競合で ID の重複・欠番が発生しうる。ファイルシステムの走査結果から毎回動的に計算することで、状態管理のインフラ（インデックスファイル）を追加せずに冪等性を確保できる。
- **トレードオフ:**
  - ファイル数 n に対する走査コストは O(n)。1000 ファイルを超えると ls の出力が顕著に増加するが、タスク管理システムでその規模に達するまでは問題にならない（実用上は n < 500 で数十ミリ秒未満）。
  - ファイル名を手動でリネームした場合、連番に欠番が生じるが、ID としての一意性は保たれる（最大値 +1 のため）。
  - 単一ライター（エージェント直列実行）を前提とする。最大値読み取りからファイル作成までの間にロックがなく、並行書込が発生すると同一 ID が採番されうる。

### 3. 優先度決定 — `tsort` 依存順序 + important/urgent bonus

- **決定:** 人間は局所的な依存関係（`depends_on`）と直感的な重要度（`important`）・緊急度（`urgent`）のみを記述する。エージェントが `tsort` でトポロジカルソートを行い、その順序を一次条件として、同一順位内でのみ重要度・緊急度を bonus として加味する。
- **代替案:** 人間が全体を俯瞰して `priority: 1〜100` の絶対評価を手動で割り振る。
- **却下理由:** タスク数が増加するにつれて全体の順序バランスを人間が維持するのは認知負荷が高く、スケールしない。人間に適した作業は「タスク B にはタスク A が必要」という局所的な依存関係の記述のみであり、全体最適化は機械に委ねるべき。
- **トレードオフ:**
  - 循環依存を検出した際の UX 設計が必要。`tsort` は循環をエラーとして報告するが、その後の修復（どの依存関係が循環を引き起こしているかの特定・提示）はエージェントの判断に委ねられる。
  - `tsort` は依存関係のエッジを持つタスクのみをソートする。独立タスク（依存関係を持たないタスク）は出力に含まれないため、オーファンのハンドリングが別途必要。

### 4. Git リポジトリ — アプリケーションコードと分離した独立リポジトリ

- **決定:** `tasks/` ディレクトリはアプリケーションコードとは完全に独立した Git リポジトリとして管理する。エージェントが mutation 操作のたびに自動的に `add / commit` を行う。
- **代替案:** アプリケーションコードと同じリポジトリ内で `tasks/` を管理する。
- **却下理由:** エージェントによる自動コミットを許容すると、アプリケーションの純粋な変更履歴が「タスクのログを追記した」「タスクを完了にした」等のノイズで汚染される。関心の分離の原則に反する。
- **トレードオフ:**
  - 初回初期化のトリガー設計が必要。`tasks/` ディレクトリが存在しない、または Git リポジトリとして初期化されていない場合のハンドリングをエージェント側で持つ（初回コミット時に自動 `git init` する等）。
  - `tasks/` の変更がアプリケーションの CI/CD 等に影響を与えないことが保証される反面、タスクとコード間の関連性を git ログから追跡しづらくなる。

## 結果

本 ADR の4つの判断により、以下の特性がシステムに与えられる:

- **ポジティブ:**
  - [判断1] 状態の不整合が設計上発生しない（アトミック性の保証）
  - [判断3] 人間の認知負荷を最小化（局所的な情報記述のみで全体最適化が機能）
  - [判断4] アプリケーションの変更履歴への影響ゼロ
  - [判断1-4] Unix 標準ツールのみで動作するポータビリティ
- **ネガティブ:**
  - [判断1] ファイル操作の直接介入による状態破損リスク（ルールベースの抑止に依存）
  - [判断2] ファイル数に比例する走査コスト（大規模タスク数での注視が必要）
  - [判断3] 循環依存検出時の UX 設計がエージェントの品質に依存

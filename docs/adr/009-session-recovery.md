# ADR 009: セッション回収アーキテクチャ

## コンテキスト

SIGINT や長時間放置によりコンテキストが失われたセッションは、自動的に回収される必要がある。回収処理では以下を行う:

- セッションログの解析と作業記録の要約
- タスクチケット（Worklog / Next Action）の更新
- ADR 候補の抽出
- WIP コミットの作成

問題点:

- 手動回収はユーザーのワーキングメモリーを圧迫する。ユーザーは回収の有無を意識したくない
- タスク管理システムへの記録はスキル（task-suspend 等）を介するため、セッション管理がタスク管理の内部構造を知らずに連携する必要がある
- ADR 抽出のタイミングと精度 -- 即時抽出はノイズが多く、バッチ抽出は遅延が大きい

## 関連 ADR

- **ADR 007:** セッションライフサイクル -- 本 ADR はセッション終了後の後処理アーキテクチャの判断
- **ADR 005:** ドキュメントレビュー基盤 -- ADR 候補の Proposed → Accepted 検証フローは ADR 管理システム（ADR 005 で定義する仕組み）の責務

## 判断

### 1. 別プロセス spawn 方式

- **決定:** 回収処理は外部トリガー（cron、systemd timer、または OpenCode 起動時フック）により、新たな OpenCode セッションを起動して実行する。起動されたセッション内で `session-recovery` スキルが回収処理を実行する。
  ```
  [trigger] → opencode session-recover --session=<session-id>
           → agent loads session-recovery skill
             → analyze session log
             → call task-suspend skill (if task exists)
             → create WIP commit (if changes exist)
             → extract ADR candidates as Proposed
  ```
- **代替案（同一プロセス内で直接タスクファイルを編集）:** cron 等のスクリプトが直接タスクファイルを読み書きする。不採用理由 -- 「セッション管理はタスク管理の内部構造を知らない」という疎結合原則（ADR 007）に反する。タスク管理のファイルフォーマット変更時にセッション管理も追随する必要が出る。
- **代替案（ユーザーの手動操作に任せる）:** ユーザーが定期的に `/session-recover` コマンドを打つ。不採用理由 -- 人間依存の運用はワーキングメモリーを圧迫し、回収漏れが発生する。基本設計の目的（ユーザーが意識せずにコンテキストが復元される）に反する。
- **理由:** 別プロセス spawn により、既存のスキル（task-suspend、task-done、create-adr）を再利用できる。回収処理そのものも 1 つのセッションとして記録されるため、回収セッションが中断した場合も同じ仕組みで再試行される。疎結合原則も守られる。
- **トレードオフ:**
  - 回収のために新しい OpenCode セッションを起動するコスト（約 1 回の LLM 呼び出し分）。放置セッション数に対して頻度は低いため許容範囲
  - 外部トリガー（cron 等）のセットアップが必要。マシン依存の設定となる
  - 回収実行中にユーザーが同じプロジェクトで新しいセッションを開始した場合のタスクチケットへの同時書き込み競合は詳細設計で対処

### 2. ADR 抽出はセッション終了時に Proposed で

- **決定:** ADR 候補の抽出はセッションクローズ/回収時に実行し、Proposed ステータスで作成する。
- **代替案（ユーザー手動）:** ユーザーが定期的にセッションログを確認し、手動で ADR を作成する。不採用理由 -- 取りこぼしリスクが高く、ユーザーの負担になる。
- **代替案（バッチ処理）:** 週次等の定期バッチで複数セッションを横断的に分析する。不採用理由 -- 遅延が大きく、判断のコンテキストが時間と共に薄れる。バッチ処理の実装コストも高い。
- **理由:** セッションのコンテキストが最も新鮮なタイミング（クローズ/回収時）に抽出することで、判断の根拠を正確に捉えられる。ノイズ（過剰抽出）は ADR 管理システム（ADR 005 で定義する仕組み）側の GC（ガベージコレクション: 長期放置 Proposed の自動破棄）で吸収する。
- **トレードオフ:**
  - 抽出された ADR の質はエージェントの判断に依存する。Proposed → Accepted の段階的検証フローで質を担保する（ADR 管理システム（ADR 005）の責務）
  - 大量に生成された Proposed ADR の管理コスト

### 3. サイレント完結

- **決定:** 回収処理は人間の確認を介さずサイレントに完結する。作業ログと残タスクは構造化データとして記録されており、LLM による要約の誤りはタスクチケットの Worklog（append-only）で後から訂正可能なため、人間の即時確認は不要と判断した。
- **代替案:** 回収結果をユーザーに逐次確認する。不採用理由 -- ワーキングメモリーの圧迫、回収の自動化目的に反する。
- **理由:** ユーザーは回収の有無を意識する必要がない。回収結果はタスクチケットに記録され、次のセッション開始時のコンテキスト収集で自然に拾われる。
- **トレードオフ:** 回収処理が誤った要約を生成しても、ユーザーが気づくのは次のセッション開始時になる。ただしタスクチケットの Worklog は append-only であり、誤りは新規エントリで訂正可能。

## 検討した代替案

- **フォールバック機構:** 回収 spawn が失敗した場合に備えて、別の回収方式（直接ファイル編集）を用意する案。不採用理由 -- 放置セッションが回収されなくても次回の定期実行で再試行される。失敗の影響は限定的であり、フォールバックを用意する複雑さのコストに見合わない。

各ステップ（スキル呼び出し、WIP コミット、ADR 作成）の失敗はベストエフォートとし、失敗したステップはスキップして後続に進む。すべての失敗は次回の定期実行で再試行される。この方針の詳細（再試行回数、冪等性の保証）は詳細設計で規定する。

## 結果

### ポジティブ

- 回収処理が完全自動化され、ユーザーは回収を意識する必要がない
- 既存スキルの再利用により、セッション管理とタスク管理の疎結合が保たれる
- ADR 抽出が Proposed で行われるため、判断の取りこぼしリスクが低い
- 回収結果が次のセッションのコンテキスト収集で自然に拾われる循環構造

### ネガティブ

- 外部トリガーのセットアップがマシン依存（cron / systemd）
- 回収セッションの起動コスト（LLM 呼び出し 1 回分）
- Proposed ADR のノイズが増える可能性（ADR 管理システム（ADR 005）の GC に依存）
- 回収誤りへのユーザー検知が遅れる

# ADR 009: セッション回収アーキテクチャ

## コンテキスト

SIGINT による強制終了、または長時間放置によりユーザーがコンテキストを失ったセッションは、自動的に回収される必要がある。回収処理では以下を行う:

- セッションログの解析と作業記録の要約
- タスク管理システムの更新
- ADR 候補の抽出
- WIP コミットの作成

問題点:

- 手動回収は面倒な作業であり回収漏れが発生しやすい。ユーザーは回収の有無を意識したくない
- タスク管理システムへの記録はそのシステムのスキルを介するため、セッション管理がタスク管理の内部構造を知らずに連携する必要がある
- ADR 抽出のタイミングと精度 -- 即時抽出はノイズが多く、バッチ抽出は遅延が大きい

## 関連 ADR

- **ADR 007:** セッションライフサイクル -- 本 ADR はセッション終了後の後処理アーキテクチャの判断
- **ADR 005:** ドキュメントレビュー基盤 -- ADR 候補の Proposed → Accepted 検証フローは ADR 管理システムの責務

## 判断

### 1. 別プロセス spawn 方式

- **決定:** 回収処理は外部トリガー（cron、systemd timer、または OpenCode 起動時フック）により、新たな OpenCode セッションを起動して実行する。起動されたセッション内で `session-recovery` スキルが回収処理を実行する。
  ```
  [trigger] → spawn a recovery OpenCode session
           → load session-recovery skill
             → analyze session log
             → call task management system skill (if task exists)
             → create WIP commit (if changes exist)
             → extract ADR candidates as Proposed
  ```
- **理由:** 別プロセス spawn により、既存のスキルを再利用できる。回収処理そのものも 1 つのセッションとして記録されるため、メタ回収（回収の回収）のチェーンが自然に構築される。疎結合原則も守られる。
- **代替案:**
  - 同一プロセス内で直接タスクファイルを編集する方式: cron 等のスクリプトが直接タスクファイルを読み書きする
    - **不採用理由:** 疎結合原則（ADR 007）に反し、タスク管理のファイルフォーマット変更時にセッション管理も追随する必要が出るため
- **代替案:**
  - ユーザーの手動操作に任せる: ユーザーが定期的に `/session-recover` コマンドを打つ
    - **不採用理由:** 人間依存の運用は回収漏れが発生しやすく、基本設計の目的（ユーザーが意識せずにコンテキストが復元される）に反するため
- **トレードオフ:**
  - 回収のために新しい OpenCode セッションを起動するコスト（∼ 1回の LLM 呼び出し分）。放置セッション数に対して頻度は低いため許容範囲
  - 外部トリガー（cron 等）のセットアップが必要。マシン依存の設定となる
  - 回収実行中にユーザーが同じプロジェクトで新しいセッションを開始した場合の競合は詳細設計で対処

### 2. ADR 抽出はセッション終了時に Proposed で

- **決定:** ADR 候補の抽出はセッションクローズ/回収時に実行し、Proposed ステータスで作成する。
- **理由:** セッションのコンテキストが失われる前に記録できる。ただし生成誤りは避けられず人間レビューが前提となる。ノイズ（過剰抽出）は ADR 管理システム側のガベージコレクション（長期放置 Proposed の自動破棄）で吸収する。
- **代替案:**
  - ユーザー手動方式: ユーザーが定期的にセッションログを確認し、手動で ADR を作成する
    - **不採用理由:** 取りこぼしリスクが高く、ユーザーの負担になるため
- **代替案:**
  - バッチ処理方式: 週次等の定期バッチで複数セッションを横断的に分析する
    - **不採用理由:** 遅延が大きく、判断のコンテキストが時間と共に薄れるうえ、バッチ処理の実装コストも高いため
- **トレードオフ:**
  - 抽出された ADR の質はエージェントの判断に依存する。Proposed → Accepted の段階的検証フローで質を担保する（ADR 管理システムの責務）
  - 大量に生成された Proposed ADR の管理コスト

### 3. サイレント完結

- **決定:** 回収処理は人間の確認を介さずサイレントに完結する。事実（作業ログ、残タスク）の把握は構造化データの要約であり、誤りは append-only で訂正可能。
- **理由:** ユーザーは回収の有無を意識する必要がない。回収結果はタスク管理システムに記録され、次のセッション開始時のコンテキスト収集で自然に拾われる。
- **代替案:**
  - 回収結果をユーザーに逐次確認する
    - **不採用理由:** 回収の自動化目的に反するため
- **トレードオフ:** 回収処理が誤った要約を生成しても、ユーザーが気づくのは次のセッション開始時になる。ただしタスク管理システムの Worklog は append-only であり、誤りは新規エントリで訂正可能。

## 検討した代替案

- **代替案:**
  - フォールバック機構: 回収 spawn が失敗した場合に備えて、別の回収方式（直接ファイル編集）を用意する
    - **不採用理由:** 放置セッションが回収されなくても次回の定期実行で再試行されるため、フォールバックを用意する複雑さのコストに見合わない

## 結果

### ポジティブ

- 回収処理が完全自動化され、ユーザーは回収を意識する必要がない
- 既存スキルの再利用により、セッション管理とタスク管理の疎結合が保たれる
- ADR 抽出が Proposed で行われるため、判断の取りこぼしリスクが低い
- 回収結果が次のセッションのコンテキスト収集で自然に拾われる循環構造

### ネガティブ

- 外部トリガーのセットアップがマシン依存（cron / systemd）
- 回収セッションの起動コスト（LLM 呼び出し 1 回分）
- Proposed ADR のノイズが増える可能性（ADR 管理システムのGCに依存）
- 回収誤りへのユーザー検知が遅れる

# ADR 012: 対立視点デュアルエージェントレビューパターン

## コンテキスト

設計案のレビューにおいて、単一のエージェントに「多角的な視点で評価せよ」と指示しても、出力は予定調和的な「バランスの取れた意見」に収束しがちである。特にハイエンドモデルは構造的にバランス型の回答を生成する傾向があり、真の緊張感のある対立意見を得ることが難しい。

問題点:

- 単一エージェントによる多視点レビューは、早期に総合へ収束し、鋭い批判が出ない
- 理論的観点と現実的観点はしばしば対立するが、一人のレビューアに両方を求めると中庸に落ち着く
- 異なるモデルファミリー（GPT 系と Claude 系）の哲学的傾向の違いを活かせていない

## 関連 ADR

- **ADR 002:** エージェント設計原則 — theorist / pragmatist は ADR 002 の 3 層アーキテクチャ（Role / Input / Output）に従う
- **ADR 005:** ドキュメントレビュー基盤 — 複数レビューアによる多層レビューパターンの先行事例
- **ADR 011:** deep-dive スキル — 本パターンを呼び出すオーケストレーションスキル

## 判断

### 1. 対立視点デュアルエージェント構成

- **決定:** 単一のマルチパースペクティブエージェントではなく、theorist（理論的整合性重視）と pragmatist（現実的制約重視）の 2 つの独立したサブエージェントを並列起動する。

  - **theorist**: 設計原則・アーキテクチャの整合性・拡張性の観点から評価。賞賛、理論的批判、理想的代替案、推奨、無知の知を突く問いを出力。口癖: "Theoretically,"
  - **pragmatist**: 実装の現実味・既存コードとの整合性・運用面の観点から評価。賞賛、現実的批判、現実的代替案、推奨、無知の知を突く問いを出力。口癖: "Theoretically yes, but"

  両エージェントとも hidden: true（`Task` tool 経由のみ起動）、edit/bash 権限なし。出力は自由形式の構造化散文。

- **理由:**
  - 並列起動により、最後の言葉バイアス（後に起動したエージェントが議論を支配する）を回避する
  - 構造化された出力セクションにより、両者の意見を統合しやすくする。各エージェントは賞賛・批判・代替案・無知の知質問の 4 軸で出力し、比較可能な形式を保つ
  - 2 エージェントにすることで、異なるモデルファミリーの特性を活かせる: GPT 系（theorist 向き: 直接的、コード生成最適化）と Claude 系（pragmatist 向き: 倫理的抑制、ニュアンス重視）の哲学の違いが自然な対立を生む
  - 隠しエージェントとすることで、ユーザーが `@` メンションで誤用するのを防ぐ。起動は deep-dive スキルのワークフロー内でのみ行われる
- **代替案:**
  - 単一マルチパースペクティブエージェント — 没理由: 「理論的理想を批判した後、現実的制約から再評価せよ」という逐次指示は後の意見を強くし、また単一エージェントのバランス志向により緊張感のある対立が生まれない
  - 逐次実行（theorist → pragmatist または逆） — 没理由: 順序が結果を歪める。theorist 先行なら pragmatist が「理論は正しいが…」と上から目線で総括。pragmatist 先行なら theorist が否定する形
- **トレードオフ:**
  - 2 回のハイエンドモデル呼び出しによるコスト増
  - 両エージェントが真っ向から対立した場合、統合の判断はユーザーに委ねられる（合成の自動化は行わない）

### 2. 遅延呼び出し — convergence gate

- **決定:** theorist / pragmatist は議論の初期段階では呼び出さず、Plan Frame の全フィールドに実質的内容が埋まり `answer` が `ready` になった時点でのみ起動する。起動前にユーザーに確認する。
- **理由:**
  - 希少なリソース（ハイエンドモデル）を乱用しない
  - 議論が固まっていない段階でアドバイザーを呼ぶと、出力が抽象的で具体的な価値が薄い
  - 「ここぞ」というタイミングでのみ助言を得ることで、出力の重みが増す
- **代替案:** 議論開始時に即時呼び出し — 没理由: 素案に対してのアドバイスは抽象的になりやすく、希少リソースの浪費
- **代替案:** 呼び出し判断を完全自動化 — 没理由: ユーザーが議論に満足していない段階での呼び出しを防げない。HITL 確認はユーザーに最終判断権を残す
- **トレードオフ:** 収束判定が誤ると呼び出しが行われない。Plan Frame の制約（全フィールド充足 + 一語エントリ禁止）で緩和する

### 3. モデル非依存設計

- **決定:** theorist / pragmatist のエージェント定義（`agents/*.md`）にはモデル指定や温度設定を含めず、実装パラメータはすべて `opencode.jsonc` の `agent` 設定で管理する。
- **理由:**
  - スキル定義を他プロジェクトで再利用可能にする（プロジェクトごとに利用可能なモデルが異なる）
  - ADR 001 の「skills as commands, no static dependencies」原則に合致する
- **代替案:** agent 定義にモデルを直接指定 — 没理由: プロジェクト間の移植性が損なわれる
- **トレードオフ:** agent 定義とモデル設定が分離することで、設定ミス（モデル未指定や誤指定）が発生しうる

### 4. 無知の知質問の義務化

- **決定:** 両エージェントの出力に、"Ignorance-exposing questions" セクションを必須項目として含める。これはレビュー対象の計画が見過ごしている設計次元・運用上の現実・暗黙の前提を問う 2-3 の質問であり、plan agent に「それには考えが及ばなかった」と言わせることを目的とする。
- **理由:**
  - 従来のレビュー（問題発見）に加え、メタ認知的価値（知らなかったことを知る）を提供する
  - 質問形式にすることで、回答の強制ではなく思考の喚起を目的とする（回答はユーザーと plan agent の再議論に委ねられる）
- **代替案:** 従来型の批判・提案のみ — 没理由: 問題発見と代替案提示は既存のレビューエージェントでも実現できる。deep-dive が独自に提供する価値として「思考の枠組みを広げる」ことがある
- **トレードオフ:** 質問の質はモデルの能力に依存する。ハイエンドモデルの使用によりカバーする

## 結果

### ポジティブ

- 単一エージェントレビューでは得られない緊張感のある対立意見が得られる
- 並列起動により、どちらの意見も他方に引きずられない
- 隠しエージェント + convergence gate により、希少リソース（ハイエンドモデル）の乱用を防止
- モデル非依存設計により、プロジェクト間での再利用が容易
- 無知の知質問により、レビューを超えたメタ認知的価値を提供する

### ネガティブ

- 2 エージェント呼び出しによるトークン消費とレイテンシの増加
- theorist と pragmatist が真っ向から対立した場合の統合はユーザーの判断に依存する
- エージェント定義とモデル設定の分離により、設定の一貫性維持に注意が必要

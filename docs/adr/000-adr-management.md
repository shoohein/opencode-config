# ADR 000: ADR 管理システム

## コンテキスト

タスク管理システムの設計判断が ADR 001-004 として記録されてきたが、ADR 自体のフォーマット・ステータス管理・テンプレート配置について統一された規約が存在しなかった。結果として ADR 001/002/004（日本語、`## 判断一覧` 形式）と ADR 003（英語、`## Decision` 形式）でフォーマットが分断し、セクション名やメタデータの置き場所も不統一であった。

ADR 作成の自動化も検討されていなかった。既存の `create-agent` / `create-command` / `create-skill` は OpenCode 固有アーティファクトの scaffolding を提供するが、ADR は OpenCode 外でも読まれうる汎用的なドキュメントであり、異なる設計方針が求められる。

本 ADR では、ADR 管理システム全体の規約を定義する。

## 関連 ADR

なし（最初の ADR）

## 判断

### 1. テンプレート形式と配置

- **決定:** `docs/adr/_template.md` にテンプレートを配置する。`_` prefix により番号付き ADR（`NNN-*.md`）より前にソートされる。テンプレートは日本語で記述し、各セクションに HTML コメントで説明を付与する。
- **代替案:** テンプレートを `create-adr` スキル内のみに保持する（`create-agent` 等と同様の方式）。
- **理由:** ADR は OpenCode 外からも読まれうる汎用的なドキュメントであり、テンプレートが `docs/adr/` に存在することでエージェントを介さず人間が直接 ADR を作成する際の拠り所となる。スキル内に隠蔽するとこの経路が断たれる。
- **トレードオフ:**
  - テンプレートとスキルの二重管理リスク。`create-adr` スキルは `_template.md` を authority とし、built-in テンプレートは同一構造の英訳として同期する。

#### 1.1 Front Matter 定義

- **決定:** ADR のメタデータを YAML Front Matter で管理する。フィールド: `status`（必須）、`date`（必須）、`tags`（必須）、`superseded_by`（`status: Superseded` の場合のみ必須）。
- **代替案:** メタデータを本文のインライン記述（`- **Status**: Accepted`）で管理する。
- **理由:** 機械処理（スキルによる検証・一覧表示）において構造化データへのアクセスが容易になる。タスク管理システムと Front Matter の使用を一貫させる。
- **トレードオフ:** 既存 ADR 001-004 への Front Matter 遡及追加が必要（別途対応）。

#### 1.2 テンプレートの実例値規約

- **決定:** `_template.md` の Front Matter 値は実例（`date: 2026-07-07`, `tags: [architecture]`）を用い、テンプレート冒頭の HTML コメントで「全値の置換が必要」であることを明示する。
- **代替案:** プレースホルダー表記（`date: YYYY-MM-DD`, `tags: [category]`）を用いる。
- **理由:** 実例値は人間にとって読みやすく、コピー後の誤った値の残留も検出しやすい。冒頭コメントにより「そのまま使ってはいけない」ことは機械的にも人間にも伝達される。

#### 1.3 必須/任意セクションの区別

- **決定:** 必須セクションには HTML コメントで説明のみ、任意セクションには `<!-- optional: ... -->` のマーカーを付与する。マーカーは言語非依存の `optional:` キーワードを用いる。
- **代替案:** セクション名のパターンマッチで必須/任意を判定する。
- **理由:** `optional:` マーカーにより、スキルは任意の言語のテンプレートから必須/任意を機械的に判定できる。パターンマッチでは言語ごとにルールが必要になり、`create-adr` の built-in 英語テンプレートとプロジェクト日本語テンプレートでロジックが分岐する。
- **結果:** 現在のテンプレートでは `コンテキスト`、`判断`、`結果` が必須、`関連 ADR`、`検討した代替案`、`関連文書` が任意。

### 2. ステータス管理体系

- **決定:** 5 値（`Proposed`, `Accepted`, `Rejected`, `Deprecated`, `Superseded`）を Front Matter の `status` で管理する。ディレクトリ分割は行わない（タスク管理と異なる）。
- **代替案:** タスク管理と同様に `proposed/` / `accepted/` 等のディレクトリ分割で状態を表現する。
- **理由:**
  - ADR 間の相互参照（「ADR 004 は ADR 002 を参照」）が状態変化で破壊されない
  - 一覧性（`ls docs/adr/` で全 ADR がフラットに見える）が維持される
  - ADR の状態遷移はほぼ 1 回限り（Proposed → Accepted / Rejected）であり、タスクのような頻繁な状態変更が発生しない
- **トレードオフ:** ディレクトリ分割しないことで「未承認の ADR だけ見たい」といったフィルタリングはファイル名一覧から直接はできない。スキルによる `status` 検索で代替する。

#### 2.1 各ステータスの意味

| 値           | 意味                                                      |
| ------------ | --------------------------------------------------------- |
| `Proposed`   | 提案段階。議論中                                          |
| `Accepted`   | 承認済み。有効な決定                                      |
| `Rejected`   | 検討の結果棄却。記録として残す                            |
| `Deprecated` | 全体として非推奨。状況変化による自然陳腐化                |
| `Superseded` | 全体が別 ADR に置換された。`superseded_by` で置換先を明示 |

- **決定:** `Superseded` の場合は Front Matter に `superseded_by: "NNN"` を追加し、置換先 ADR の番号を明示する。
- **理由:** 機械処理で「この ADR の現行版はどれか」を即座に判定できる。

### 3. ID とファイル命名

- **決定:** 3 桁ゼロパディングの連番 ID（`000`, `001`, `002`, ...）を採用し、ファイル名は `NNN-slug.md` とする。`000` は本 ADR のようなメタ ADR 用に予約する。
- **代替案:** 4 桁連番、日付ベースの ID、手動採番。
- **理由:**
  - 3 桁はタスク管理と一貫した規約
  - 自動採番（全 ADR の最大 NNN + 1）が単純かつ冪等
  - slug によりファイル名から内容の推測が可能
- **トレードオフ:** ID の欠番（ファイル削除時）が発生しうるが、一意性は保たれる

### 4. 置換方式

- **決定:** ADR の置換は全体置換のみを認める。部分置換（特定の決定項目だけを上書き）は禁止する。
- **代替案:** 部分置換を許容し、新 ADR の Front Matter に `supersedes: [{adr: "002", decision: "4"}]` を記述する。
- **理由:** 部分置換は読む側にとって「現在の正しい状態」の再構築コストが高すぎる。古い ADR と新しい ADR の間で「どの決定が生きていて、どれが無効か」を脳内差分計算する必要が生じる。多少内容が重複しても、各 ADR を自己完結的な文書として全体置換する方が管理しやすい。
- **トレードオフ:**
  - ADR 004（コマンド設計原則）のように、既存 ADR の一部だけを置き換えたいケースでも全判断を再掲する必要がある。ただし実際には置換対象以外の判断もレビューされる機会となり、文書の鮮度維持に寄与する。
  - **置換の相互参照:** 旧 ADR 側は Front Matter に `status: Superseded` + `superseded_by: "NNN"` を持つ。新 ADR 側は `## 関連 ADR` に置換元 ADR を prose で記述する。この非対称性は意図的である — 旧 ADR 側は機械可読（ツールが即座に現行版へ誘導）、新 ADR 側は人間可読（文脈説明）の責務分担。

### 5. スキルとの関係

- **決定:** `create-adr` スキルを作成し、ADR の scaffolding を自動化する。スキルは `_template.md` を authority とし、プロジェクト固有テンプレートが存在しない場合の fallback として built-in テンプレート（英語、同一構造）を持つ。
- **代替案:** スキルを作成せず、`_template.md` の手動コピーに依存する。
- **理由:** 既存の `create-agent` / `create-command` / `create-skill` と一貫した scaffolding パターンを提供し、ID 採番・Front Matter 検証・セクション充足確認を自動化する。
- **トレードオフ:**
  - スキルとテンプレートの二重管理リスク。built-in テンプレートを `_template.md` の英訳と同一構造に保つ運用規律が必要。

#### 5.1 テンプレート発見と優先順位

- **決定:** ADR ディレクトリの探索順序を以下とする:
  1. `documentation-policy.md` 等の instruction ファイルから ADR ディレクトリパスを抽出
  2. convention 探索: `docs/adr/`, `doc/adr/`, `adr/` の順に `NNN-*.md` の存在を確認
  3. いずれも見つからなければユーザーに確認
- **決定:** 発見したディレクトリに `_template.md` があれば project override として使用し、なければ built-in テンプレートで新規作成する。
- **理由:** instruction ファイルが ADR ディレクトリを明示している場合はそれに従い、明示がない場合は convention で発見する。`_template.md` の override によりプロジェクト固有のフォーマットを尊重する。

#### 5.2 検証ポリシー

- **決定:** Front Matter の構文・必須フィールド検証は hard error として作成をブロックする。セクション充足（必須 H2 の不足）は warning として通知し、ユーザー確認を経て作成を許可する。
- **理由:** Front Matter の誤りは機械処理を阻害するためブロックが妥当。セクションの不足は「意図的な省略」の可能性を排除できないため、ユーザー判断に委ねる。
- **結果:**
  - hard error: `status` 不在/不正値、`date` 不在/不正フォーマット、YAML 構文エラー
  - warning: 必須セクション（`optional:` マーカーなしの H2）の不在

#### 5.3 `documentation-policy.md` との関係

- **決定:** `documentation-policy.md` は「いつ ADR を作成するか」のみを指示し、`create-adr` スキルを明示的に参照しない。スキル発見は available_skills の説明文一致による自然な解決に委ねる。
- **理由:** `documentation-policy.md` がスキルを参照すると「何を使って ADR を作るか」を instruction が知ることになり責務が混在する。また `create-adr` が `documentation-policy.md` からディレクトリパスを抽出する前提との循環参照を回避する。

#### 5.4 言語方針

- **決定:** built-in テンプレートは英語固定。プロジェクトの `_template.md` は任意の言語を許容する。`create-adr` スキルはテンプレートの言語を強制しない。
- **理由:** built-in に英語を用いるのは `create-agent` / `create-command` / `create-skill` の英語統一ルールとの整合性のため。一方、ADR の本文はプロジェクトの primary language で書かれるべきであり、スキルが言語を押し付けるべきではない。

## 結果

### ポジティブ

- ADR のフォーマット不統一が解消され、作成・レビュー・参照の一貫性が確保される
- `create-adr` スキルにより ID 採番・検証・ファイル作成が自動化され、作成コストが低下する
- `_template.md` が `docs/adr/` に存在することで、エージェントを介さない手動作成もサポートされる
- `optional:` マーカーにより、任意言語のテンプレートから必須/任意セクションを機械的に判定できる
- 全体置換のみを認めることで、ADR 間の依存関係が単純化し、読む側の認知的負荷が低減する

### ネガティブ

- 既存 ADR 001-004 への Front Matter 遡及追加が必要（別途対応）
- `_template.md` と built-in テンプレートの二重管理リスク（運用規律で緩和）
- 部分置換禁止により、一部のみを更新したい場合でも全判断の再掲が必要になる
- 新規 ADR ディレクトリ（`_template.md` 未存在）の初回セットアップがやや複雑

# セッション管理システム 基本設計書

## 目的

AIエージェントと協働する中で無数に生まれる OpenCode セッションを管理し、作業の効率化を図る。ユーザーはセッションの詳細を気にせず、「続きをやって」と指示するだけで前回のコンテキストが復元される UX を実現する。

## 前提条件

本システムは以下の外部システムに依存する。いずれかが不在の場合、該当する機能は縮退する（縮退時の挙動は後述）。

| システム           | 所在        | 不在時の挙動                              |
| ------------------ | ----------- | ----------------------------------------- |
| タスク管理システム | `tasks/`    | コンテキスト収集とタスク更新をスキップ    |
| ADR 管理システム   | `docs/adr/` | ADR 候補の抽出をスキップ                  |
| Git リポジトリ     | `./.git`    | git 依存機能（notes、コミット）をスキップ |

セッションログの永続化は OpenCode 自身の責務であり、本システムでは行わない。

## 設計原則

### Stateless Session Operation

セッションを読み返すのは人間にとって認知負荷が高く、セッション再開のたびにエージェントに要約させるのもトークンの無駄である。このため、セッション自体は内部状態を持たず、必要なコンテキストは**次のセッション開始時に外部から収集**する。

なお、セッション一覧での視認性のため、セッションのタイトルには接頭辞（`【完了】`、`【中断】`）で大まかな状況を表示する。これはセッションの「状態」ではなく、人間のための表示ラベルである。

### Single Source of Truth（SSoT）は現状

コンテキスト収集の情報ソースは、**現在のワーキングツリー、git log、タスクチケット**とする。過去のセッション記録を別ファイルで二重管理すると、OpenCode 本体のセッション状態との不一致や、古い情報によるトークン浪費を招くためである。

### 疎結合

セッション管理システムはタスク管理システムや ADR 管理システムの内部構造（ファイルパス、フロントマター形式）を知らない。連携はすべて**スキル呼び出し**を介する。

## セッションライフサイクル

### 1. 開始：コンテキスト収集

エージェントは instruction に従い、以下の情報を収集する。

| 情報源             | 内容                                          |
| ------------------ | --------------------------------------------- |
| `git status`       | ワーキングツリーの状態                        |
| `git log`          | 直近のコミット履歴                            |
| タスク管理システム | 進行中タスクの `📍 Next Action`、`📝 Worklog` |

**収集の要不要**：

| ユーザー指示の性質                                | 収集               |
| ------------------------------------------------- | ------------------ |
| 単一ファイルの機械的編集                          | スキップ           |
| 自己完結的なコマンド（commit 等）                 | スキップ           |
| 純粋な情報照会                                    | スキップ           |
| 漠然とした指示、複数ファイル/ステップが予想される | 実行               |
| 作業継続を示唆（"続き"、"resume" 等）             | 実行               |
| それ以外                                          | 実行（デフォルト） |

この基準は instruction に設定可能なデフォルトとして記述し、プロジェクト/ユーザー単位で上書き可能とする。

### 2. 終了：クローズ処理

#### 2.1 正常終了

ユーザーが明示的にセッションを閉じる場合、`session-close` スキルが以下を実行する：

1. タイトルを内容に合致するよう更新し、接頭辞 `【完了】` を付与
2. 変更があり未コミットの場合、WIP（Work In Progress）コミットを作成
3. 進行中タスクがある場合、`task-done` スキルを呼び出す
4. セッション中の判断を ADR 候補として抽出し、Proposed ステータスで作成する

#### 2.2 セッション回収

SIGINT や長時間放置によりコンテキストが失われたセッションは、セッション回収システムが自動的に回収する。

1. 放置セッションを発見し、新たな OpenCode セッションを起動
2. `session-recovery` スキルを実行する：
   - タイトルを更新し、接頭辞 `【中断】` を付与
   - セッションログを解析し、作業記録を要約
   - 進行中タスクがある場合、`task-suspend` スキルを呼び出す
   - 変更があり未コミットの場合、WIP コミットを作成
   - ADR 候補を抽出し、Proposed ステータスで作成する

回収処理は人間の確認を介さずサイレントに完結する。ユーザーは回収の有無を意識する必要はない。回収結果はタスクチケットの Worklog と Next Action に記録されるため、次のセッション開始時のコンテキスト収集で自然に拾われる。

### 3. ADR 候補のライフサイクル

セッション終了時に抽出された ADR 候補は Proposed ステータスで作成される。Proposed → Accepted への検証、および長期放置された Proposed の自動破棄は ADR 管理システムの責務である。本システムは抽出と作成までを行う。

## セッション追跡

セッションのトレーサビリティ情報は `git notes` としてコミットに付与する。対象は、タスク管理プラグインが自動生成するタスク管理リポジトリへのコミットである。

```bash
git notes add -m '{"session":"calm-eagle"}' <task-commit-hash>
```

`git notes` はデフォルトで `push` 対象外であり、ローカル情報を他マシンに拡散しない。

未コミットで中断されたセッションについては、コミットが存在しないため git notes を付与できない。このケースのトレーサビリティは諦める。

## セッション回収の実行基盤

### トリガー方式

定期的な自動実行を基本とする。具体的な実装方式（cron、systemd timer、OpenCode 起動時フック、またはこれらのハイブリッド）は詳細設計で決定する。

### リソース分離

回収処理はユーザーのメイン作業を阻害しないよう、別プロセスとして実行する。ADR 候補の抽出には論理的思考力を要するため、安価すぎるモデルは使用しない。具体的な実装方式は詳細設計で決定する。

## 実装アーキテクチャ

| レイヤー    | 責務                                       | 成果物                           |
| ----------- | ------------------------------------------ | -------------------------------- |
| Plugin      | 状態変更（タイトル更新、git notes 付与）   | `@opencode-ai/plugin`            |
| Instruction | ツール使用判断（コンテキスト収集の要不要） | `instructions/session-status.md` |
| Skill       | 手順（session-close、session-recovery）    | `.opencode/skills/`              |
| Command     | ユーザー向けラッパー                       | `.opencode/commands/`            |

# ファイルシステム・ベース・タスク管理システム 基本設計書

## 1. システム概要

### 1.1 目的

本システムは、OpenCode 環境で動作するプログラマのための自律型タスク管理アシスタントである。プログラマの三大美徳（怠惰・短気・傲慢）と Unix 哲学（1 つのことをうまくやる、テキストストリームをパイプで繋ぐ）を体現し、タスクの状態管理・優先順位決定・作業ログ管理をファイルシステム操作と標準 Unix コマンドで実現する。

### 1.2 基本設計のスコープ

本設計書はシステム全体のアーキテクチャと構成要素の定義を扱う。個々の処理の詳細ロジック、実装上のアルゴリズム、エージェントツールの具体的な実装方式は詳細設計に委ねる。

## 2. アーキテクチャ

### 2.1 ディレクトリ構成

```
tasks/                    # Git 独立リポジトリ（アプリケーションコードとは分離）
├── pending/              # 未着手キュー
├── in_progress/          # 作業中
├── done/                 # 完了済（成功）
├── canceled/             # 破棄・Wontfix
└── archive/              # 状態ではない補助ディレクトリ（将来拡張用）
```

各ディレクトリ内にはタスクファイル（`.md`）が格納される。状態を示すインデックスファイルや status.md 等のメタファイルは作成しない。

### 2.2 状態不変条件（State Invariants）

1. **唯一の状態:** タスクの「状態」は所属ディレクトリのパスが唯一の真実の源泉である。
2. **メタデータ禁止:** YAML Front Matter に `status` フィールドを絶対に含めてはならない。状態情報の二重管理を設計レベルで禁止する。
3. **アトミック遷移:** 状態変更は常に `mv` コマンドで行う。ファイルの内容は移動前後で書き換えない（完了日の追記を除く）。
4. **明示的トリガー:** 状態遷移はユーザからの明確な完了・破棄の指示があった場合のみ実行する。

## 3. データモデル

### 3.1 ファイル命名規則

```
[3桁連番]-[short-kebab-name].md
```

例: `001-setup-database.md`, `042-implement-auth.md`

連番は `tasks/` 配下（`archive/` 含む全ディレクトリ）の `.md` ファイルを走査し、最大値 +1 を動的に算出する。

### 3.2 YAML Front Matter

すべてのタスクファイルは先頭に YAML Front Matter 形式でメタデータを持つ。

```yaml
---
description: 1行の概要
created_at: YYYY-MM-DD
important: true # true / false
urgent: true # true / false
depends_on: # YAML リスト形式（3桁IDのみ）
  - 001
  - 015
---
```

完了時には `completed_at` が追記される:

```yaml
---
description: 1行の概要
created_at: YYYY-MM-DD
completed_at: YYYY-MM-DD
important: true # true / false
urgent: true # true / false
depends_on:
  - 001
  - 015
---
```

| フィールド | 必須 | タイプ | 説明 |
| --- | --- | --- | --- |
| `description` | 常時 | 文字列 | タスクの1行概要 |
| `created_at` | 常時 | 日付 | 作成日 |
| `completed_at` | 完了時のみ | 日付 | 完了日（`sed` で冪等追記） |
| `important` | 常時 | 真偽値 | 重要フラグ |
| `urgent` | 常時 | 真偽値 | 緊急フラグ |
| `depends_on` | 任意 | リスト | 依存タスクの識別子リスト。存在しない ID や done/canceled の ID は指定不可（作成時バリデーション） |

### 3.3 本文の2層構造

#### `# 📍 Next Action`（上部）

ユーザの現在の思考・次に取るべきアクションを記述する領域。 **エージェントはユーザから明示的な指示・委譲がない限り、この領域を書き換えてはならない。**

#### `# 📝 Worklog`（下部）

作業経過を記録する追記専用領域。

- 標準出力をそのまま貼り付けることは禁止。
- 「何が起きたか」「どう解決したか」の意味のみを抽出し、簡潔なリスト形式で追記する。

### 3.4 サブタスク

YAML Front Matter の直後から `# 📍 Next Action` の直前までの `- [ ]` / `- [x]` リスト形式の行をサブタスクとして扱う。`# 📍 Next Action` および `# 📝 Worklog` 内のチェックリストは集計対象外。進捗率は `grep` でこれらを集計し動的に計算する。

## 4. コンポーネント定義

### 4.1 機械的コンポーネント（Mechanical）

Unix 標準コマンドで完全に自動化・固定化できる処理。

| コンポーネント | 責務 | 入力 | 出力 | 備考 |
| --- | --- | --- | --- | --- |
| **ID採番** | 全ディレクトリの `.md` を走査し、ファイル名の3桁連番の最大値 +1 を算出する | なし（ファイルシステム走査） | 次 ID（3桁連番） | `archive/` も走査対象に含む |
| **状態遷移** | タスクファイルを `mv` で該当ディレクトリに移動する。`done/` へ移動時は `sed` で `completed_at` を YAML に冪等追記する | タスクファイルのパス + 移動先ディレクトリ | なし（副作用のみ） | トリガーは常にユーザの明示指示 |
| **進捗計算** | `grep` で `- [ ]` と `- [x]` をカウントし完了率を算出する | タスクファイルのパス | 進捗率（例: 3/5 = 60%） | サブタスク定義にのみ依存 |
| **依存解析** | `pending/` 内の全タスクから `depends_on` を `awk` で抽出し、`tsort` でトポロジカルソートする | `pending/` ディレクトリ | ソート済みタスクリスト | 循環依存検出時は即座にエラー報告（絶対に握りつぶさない） |

### 4.2 エージェント振る舞い（Agent Behaviors）

LLM による文脈理解・判断が必要な処理。

| 振る舞い | 責務 | 備考 |
| --- | --- | --- |
| **次タスク提案** | 依存解析の結果（`tsort` 順序）を一次条件とし、`important: true` / `urgent: true` を二次的な 加点 として加味した上で、最も着手すべき1件を人間に言語化して提示する | トポロジカル順序が必須の基底であり、重要度・緊急度は同一順位内での 加点 に過ぎない |
| **ワークログ要約** | 作業の生ログや会話から「何が起きたか」「どう解決したか」の意味を抽出し、`# 📝 Worklog` セクションに簡潔なリスト形式で追記する | Append-only。既存 Worklog の書き換え禁止 |
| **task-suspend（中断委譲）** | ユーザから明示的な中断指示と委譲を受けて、Worklog の文脈から `# 📍 Next Action` を最新状態に要約・更新する | ユーザからの明示的委譲がない限り Next Action を書き換えてはならない |

## 5. 主要判断の根拠（Rationale）

判断の背景とトレードオフは ADR 001・002 を参照。

### なぜ「状態」をメタデータではなくディレクトリ移動（`mv`）で表現するのか

メタデータ内に `status: in_progress` を持たせながら同時にディレクトリ配置も行う設計は、データの二重管理（DRY 違反）である。必ず「ディレクトリは done/ なのにファイル内は pending のまま」という不整合が発生する。Unix の `mv` はアトミックな操作であり、ディレクトリ構造そのものを状態マシンとすることで、ステータス同期のバグを設計レベルで排除する。

### なぜタスクの優先度に `tsort` を用いるのか

人間が数十個のタスクを俯瞰して絶対評価の優先度を割り振ることは認知負荷が高く、誤りがちである。人間が正確に判断できるのは「タスク B にはタスク A が必要」という局所的な依存関係のみ。依存関係から導かれる着手可能順序の決定は `tsort` という単一目的の Unix ツールが行うべき仕事である。`tsort` はあくまで依存順序を算出するものであり、最終的な優先順位はその順序を基底として別途決定する。

### なぜ Next Action と Worklog を分離するのか

作業を再開した際に長大なログを読み直すオーバーヘッドを避けるため。ファイル上部の Next Action を「現在地」、下部の Worklog を「不変の過去」として分離することで、数秒でコンテキストを復元できる。また生ログではなく意味抽出結果のみを記録することで、テキストの検索性（`grep`）を維持する。

### なぜタスク群を別リポジトリで管理するのか

アプリケーションの変更履歴とタスク操作（完了・ログ追記など）の履歴を分離するため。同じリポジトリで管理すると、ソースコードの pure な変更履歴がタスク管理ノイズで汚染される。タスク専用の独立した Git リポジトリとし、エージェントが裏で自動的に `add/commit` を行うことで、ユーザに Git の存在を意識させずにバージョン管理の恩恵だけを提供する。

### なぜ標準 Unix コマンド（`bash`, `grep`, `awk`, `tsort`）にこだわるのか

タスク管理のために専用のデータベースや重厚なスクリプトを必要としない。行指向のテキストファイルと 50 年以上鍛え上げられてきた Unix 標準コマンドの組み合わせが最もポータブルで予測可能であり、壊れにくい。エージェントにもこの哲学を適用することでブラックボックス化を防ぎ、人間がいつでも介入・デバッグできる透明性を担保する。

## 6. ワークフロー概略

本節では主要な操作フローの概略のみを示す。詳細なステップ・疑似コード・エラーハンドリングは詳細設計に委ねる。

### 6.1 タスク作成フロー

1. ID採番コンポーネントが次 ID を動的算出
2. テンプレートに従いタスクファイルを作成し `pending/` に配置
3. 自動 Git commit

### 6.2 タスク開始フロー

1. ユーザからタスク開始の明示指示を受ける
2. `tasks/pending/` から `tasks/in_progress/` へ移動
3. 自動 Git commit

### 6.3 タスク完了フロー

1. ユーザから完了の明示指示を受ける
2. `tasks/in_progress/` から `tasks/done/` へ移動し、YAML に `completed_at` を冪等追記
3. 自動 Git commit

### 6.4 タスク破棄フロー

1. ユーザから破棄・Wontfix の明示指示を受ける
2. `tasks/in_progress/`（または `tasks/pending/`）から `tasks/canceled/` へ移動
3. 自動 Git commit

### 6.5 次タスク提案フロー

1. ユーザから「次なにやる？」の問い合わせを受ける
2. 依存解析コンポーネントが `pending/` をトポロジカルソート
3. エージェントが重要度・緊急度を 加点 として加味し、最適な1件を言語化して提示

### 6.6 中断・再開フロー

1. ユーザが `task-suspend` を呼び出し、中断するタスクと委譲を明示的に指示
2. エージェントが Worklog を読み取り、Next Action を要約・更新
3. 再開時は Next Action を読むだけで即座にコンテキスト復帰
